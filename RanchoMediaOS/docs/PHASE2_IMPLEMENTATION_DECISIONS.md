# Phase 2 implementation decisions

Baseline: local commit `3af20b3`. The nine requested baseline documents were read before implementation. Upstream pins and Phase 1 designs remain frozen.

1. **API-only**: the new instruction explicitly permits API-only instead of MVP_PLAN's UI. No React work, browser or real authentication. Development/test requests identify the local human fixture with `X-Actor-ID`; this is trusted local identity, not production authentication. Production environment and automatic approval are refused. Listen on loopback only.
2. **Infrastructure**: Docker remains blocked. File-backed SQLite is an explicitly labelled offline test/development backend, never PostgreSQL qualification. Core and mock have separate databases, connections and transactions. Alembic owns both schema subsets. PostgreSQL DDL/offline migration is checked; live migration remains `PENDING_DOCKER`. No Docker repair or native database workaround.
3. **States**: Phase 1 job states remain authoritative: `SCHEDULED`, `DISPATCHING`, `PUBLISHED`, `FAILED_RETRYABLE`, `FAILED_TERMINAL`, `OUTCOME_UNKNOWN`, `NEEDS_HUMAN`, `CANCELLED`. API `outcome=SUCCEEDED` means persisted `PUBLISHED`; it is not a second mutable state machine. Effect ledger uses `PREPARED`, `IN_FLIGHT`, `UNKNOWN`, `CONFIRMED`, `FAILED`. Unknown/in-flight recovery performs lookup only; absence never licenses a resend.
4. **Approval**: approval binds immutable variant payload, account and UTC schedule. Editing creates a new revision and revokes the old approval. Every dispatch rechecks approval. Deterministic fixture generation and review exercise mechanics only; they do not qualify real editorial/fact/similarity gates.
5. **Analytics**: retain conservative Phase 1 baseline cohort `(platform, account, format, age)` and minimum 20 distinct publications. Missing and zero denominators yield null. No fabricated percentile. Small sample performance may change *exploratory* candidate ranking, with explicit uncertainty; it never promotes a strategy or claims significance. Strategy separates SQL facts, hypotheses and recommendations.
6. **Mock time**: simulated age is explicit, deterministic and persisted. `captured_at` is the injected observer's UTC time; `simulated_at` is external publish time plus simulated age. Velocities use simulated age differences, not wall time between requests. All metrics and recommendations carry simulation provenance.
7. **Workflow**: persistent in-process orchestrator/outbox with restart reconciliation replaces the unavailable Temporal server for Phase 2. Future Temporal implementation must wrap the same service methods. No Temporal replay/time-skip/server validation claimed.
8. **Layout**: retain the existing `packages/platform-sdk` directory rather than moving it to underscore spelling. Installable Python module is `rancho_platform_sdk`. No upstream application source is imported or copied.
9. **Transactions**: short local claim commit → independent mock transaction → local confirmation commit. SQL uniqueness and compare-and-set enforce concurrency, without process-local locks. No external operation runs while holding a local write transaction. See [SQLAlchemy async sessions](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html) and [Alembic metadata comparison](https://alembic.sqlalchemy.org/en/latest/autogenerate.html).

These are reversible Phase 2 boundaries, not silent substitutions for live infrastructure or platform qualification.

10. **Configuration names**: current `APP_ENV` requirement replaces the Phase 1 inventory's `RANCHO_ENV`. `.env.example` now lists only implemented settings. No `.env` file is automatically read, and no model/platform key is needed.
11. **Ordered strategy history**: proposals have owner-scoped `supersedes_id` links and unique successors, with a short database owner lock. Latest proposal follows this chain even when injected clocks return identical timestamps. Candidate IDs are deterministic UUIDs per owner/trend/strategy, so concurrent reads persist a single candidate set.
12. **Evidence consistency**: strategy averages, counts, observation window and snapshot references come from one SQL statement using windows over each publication's latest observation. Means ignore unsupported/null engagement; sample size counts observed publications, not repeated snapshots. Baselines count only valid engagement samples at the exact same age and never include the subject publication.
13. **Dispatch cutoff**: editing/rejecting before dispatch revokes approval and cancels a scheduled job. Once the immutable approved send is claimed and committed, later edits cannot undo an already initiated external effect; recovery still reconciles it. No new payload can inherit approval from that revision.

14. **SQLite approval/claim serialization**: SQLite ignores `SELECT FOR UPDATE`. Owner-scoped repository locks first reserve the SQLite writer with a no-op update of the mutable owner row, then refresh the requested record. This prevents an edit or rejection from committing between approval validation and the dispatch claim. The reservation ends at the existing short transaction commit, before the independent mock send. Adversarial tests cover both review actions racing the claim, an edit committed before the claim, and editing while the external send is paused. PostgreSQL retains its existing row lock; live PostgreSQL behavior is still unqualified.
